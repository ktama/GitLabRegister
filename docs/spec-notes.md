# 作業メモ (spec-notes) — GitLab-EE Issue 登録アプリ

## Phase 0: タスク理解

### 依頼の言い直し
GitLab-EE (自社運用の Enterprise Edition) に対して Issue を登録できる Windows 用アプリを新規開発する。
単発の Issue 登録だけでなく、「繰り返し発生するタスク」を定義しておき、定義したスケジュールに従って Issue が作られる仕組みを備える。
本タスクではコードは書かず、要件定義書を Markdown で作成する。

### 既知
- 対象は GitLab-EE (SaaS の gitlab.com ではなく自社/組織内インスタンスの想定)
- 成果物の形態は Windows アプリ
- 繰り返しタスクの設定機能が必須
- 作業ディレクトリは空でコードなし = 完全な新規開発
- 日本語で要件定義書を作る

### 未知 (質問候補)
1. 繰り返し登録の実行契機 (常駐自動 / アプリ起動時バッチ / OS スケジューラ / 手動確認)
2. 利用者の範囲 (個人の手元ツールか、チームで設定を共有するか)
3. GitLab への認証方式 (PAT / OAuth / その他)
4. 繰り返しパターンの表現力 (毎日・毎週程度か、cron 相当か、営業日・祝日考慮まで必要か)
5. 設定可能な Issue 項目の範囲 (title, description, labels, assignee, milestone, due_date, weight, epic, iteration など)
6. 対象プロジェクトの数 (単一固定か複数切替か)
7. 重複登録の防止要否
8. 登録失敗時の扱い (リトライ、通知)
9. 配布・インストール形態、GitLab インスタンスの URL やバージョン
10. 想定データ量 (繰り返しタスク定義の件数、1日あたりの登録件数)

### 前提 (未確認の仮定)
- GitLab-EE の REST API v4 がクライアント端末から HTTPS で到達可能である
- 端末のタイムゾーンは JST 固定で運用される
- UI は日本語
- 利用者は GitLab のアカウントを既に持ち、対象プロジェクトへの Issue 作成権限がある

## Phase 2: スコープ確定

- 目的: 定期的に発生する作業を繰り返し定義として登録しておき、計画時に期間を指定して GitLab-EE へ Issue をまとめて起票する手間と漏れをなくす。
- 対象範囲: 繰り返し定義の管理、期間指定による発生日展開、プレビュー、一括登録、登録履歴による重複除外、単発登録。
- 対象外 (non-goals): 常駐自動登録、OS スケジューラ連携、チームでの定義共有、Issue の参照・更新・クローズ、マージリクエスト操作、GitLab.com (SaaS) の動作保証、GitLab 以外の課題管理ツール対応。
- 優先度: 上記回答に基づき Must 12 件 / Should 5 件 / Could 2 件 / Won't は non-goals に記載。

## 追加ヒアリング (2026-10-03, 版 0.2)

| # | 論点 | 回答・決定 |
|---|---|---|
| 13 | 隔週で発生する作業がある | FR-04 のパターン 4 を「毎週・N 週ごと」とし、N=2 で隔週を表す |

### 決定した理由

初版の FR-04 は「N 週ごとの指定を含む」と書いていたが、どの週を 1 週目と数えるかを定義していなかった。
この状態では展開する期間を変えるたびに隔週のリズムが変わりうるため、要件として合否を判定できない。
そこで N 日ごとのパターンと同じく起算日を持たせ、「起算日を含む週を 1 週目とし、発生週の判定は起算日のみに依存する」と定めた。
展開期間への非依存を受け入れ基準に明示し (FR-04 の 3 番目)、起算日の変更と未来起算日の指定を EC-30、EC-31 で扱う。

### 隣接する未確認事項 (解決済み)

隔週があるなら隔月・四半期ごともありうるため OQ-08 として起票したが、2026-10-03 の確認で該当する周期は運用していないと回答を得た。

## 版 0.4: GitLab-EE 19.2 前提での未解決事項の決定 (2026-10-03)

### 公式ドキュメントで確認した事実

Issue の作成 API を 19.x のドキュメントで確認し、次を根拠として採用した。

| 確認事項 | 結果 | 反映先 |
|---|---|---|
| タイトルの上限 | 255 文字 (超過時は検証エラー) | EC-02、FR-06 |
| 説明の上限 | 1,048,576 文字 | EC-02、FR-06 |
| イテレーションの設定 | Issue の作成・更新の属性に存在しない。一覧の絞り込みと応答には存在する | 第 8 節、FR-06 |
| ラベル | 存在しない名前を指定すると GitLab 側にラベルが新規作成される | 第 8 節、EC-32、FR-16 |
| エピック・ウェイト・複数担当者 | Premium 以上で Issue 作成時に指定できる | FR-06、EC-15 |
| 開始日 | GitLab 19.1 で Issue の作成時に指定できるようになった | OQ-10 (提案) |
| 19.0 の破壊的変更 | Issue の作成・参照に影響する項目はない | 第 3 節 前提 |

### 初版の誤りを 2 件修正した

1. FR-20 の受け入れ基準に「存在しないラベルの指定が失敗の原因になる」と書いていたが、実際はラベルが自動作成されるため失敗しない。マイルストーンの例に差し替え、ラベルの自動作成は EC-32 として別に要件化した。
2. FR-06 はイテレーションを他の項目と同列に扱っていたが、Issue の作成時には指定できない。作成とは別の操作とし、イテレーションの設定だけが失敗した場合の扱いを定めた。NFR-02 の所要時間にも 1 件 2 通信になることを織り込んだ。

### 決定の方針

OQ-03 (プロキシ) と OQ-06 (配布) は利用者の環境に依存して確定できないため、どちらの環境でも成立する仕様を選んだ。
プロキシは OS 設定への追従を既定にして手動上書きを許し、配布はフォルダ展開のみで動く形にして管理者権限と社内配布基盤への依存を外した。
確認が取れていない事項は 2 件に減った (OQ-09 ライセンスティア、OQ-10 開始日の採否)。

## 版 0.5: 残る 2 件の決定 (2026-10-03)

| ID | 決定 | 影響範囲 |

### 開始日を追加するにあたって決めたこと

- 指定方法は期限と同じく発生日からの日数オフセットにした。日付の直接指定は繰り返しに向かないため。
- 営業日調整は発生日にのみ適用し、開始日と期限には適用しない。初版の期限の規則をそのまま踏襲した。
- 開始日のオフセットが期限のオフセットを超える指定は保存を拒否する (EC-36)。GitLab 側の検証に頼らず入力時に止める。
- 片方だけの指定と両方未指定を許した。GitLab はどちらか一方だけの日付を受け付けるため、アプリ側で縛る理由がない。
- FR-15 の差し込み項目は 6 つから 7 つになった (開始日を追加)。

### EC-15 の位置づけを変えた

ティアが確定したため、EC-15 は「ティアが分からない場合の退避」ではなく「ティアが Premium を下回る状態に変わった場合の退避」になった。
文言をそれに合わせた。要件自体は残す。
